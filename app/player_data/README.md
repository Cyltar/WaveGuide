# WaveGuide player evidence

## Architecture

`riot_api.py` fetches Riot Account-V1 and Match-V5 responses. `match_parser.py`
identifies the player, role counterpart and all participant teams/champions.
`timeline_parser.py` normalizes frames and selected events. `game_analyser.py`
computes metrics, keeps event evidence and emits conservative review candidates.
The future Gemini layer should consume the analysis, interpret threats and decisions,
and write coaching. It should not receive the raw timeline or redo arithmetic.

The existing British filename `game_analyser.py` is preserved. No third-party game
data, new dependencies, classes or Gemini integration were added.
The original four source files were inspected; `__pycache__` held generated bytecode.
There were no saved match/timeline JSON files or existing tests in this directory.

## Changes by file

- `match_parser.py`: retains existing match/participant output; adds lane and jungle
  CS totals and map ID; unknown or ambiguous roles no longer invent a counterpart.
- `timeline_parser.py`: permits an absent counterpart, sorts frames/events, retains
  ward records, all-player XP and non-champion damage. Damage grouping keeps source
  name and spell slot distinct. API imports now happen only in the live demo, so
  deterministic parsing needs no API key.
- `game_analyser.py`: retains economic windows, matchup/team deltas, XP, combat,
  farming, deaths and conversions, with the accuracy and schema changes below.
- `test_player_data.py`: offline synthetic regression tests, including the eight
  requested regression themes and additional edge cases.
- `riot_api.py`: supports paginated match IDs and request timeouts. Live requests
  require `RIOT_API_KEY`; importing modules for offline analysis does not.

## API and schema version 2

### Product workflows and analysis version 4

`game_analyser.py` remains authoritative for a single game. It now includes
`analysis_version`, `match_id`, `puuid`, start timestamp, duration, patch, queue,
player champion/role/team/result, `aggregate_metrics`, `pattern_occurrences`,
`death_context_counts`, `strength_signals`, and `weakness_signals`.
GD@10 and XP difference @10 use the same milestone sample as CSD@10.

`player_analyzer.py` consumes these results without network calls or raw timelines:

```python
from app.player_data.player_analyzer import analyze_player

recent_report = analyze_player(game_analyses)
champion_report = analyze_player(game_analyses, champion='Yunara')
```

Filtering a list only analyzes matches already supplied. For a request for the most
recent N champion matches, use the service, which searches further through history:

```python
from app.player_data.analysis_service import (
    analyze_specific_game, analyze_recent_games, analyze_champion,
)

last_game = analyze_specific_game(puuid)  # Or pass match_id='NA1_...'.
recent = analyze_recent_games(puuid, game_count=20)
yunara = analyze_champion(puuid, 'Yunara', game_count=20, max_matches_scanned=200)
```

All service functions accept `routing_region='americas'`. Resolve a Riot ID to PUUID
with the existing `riot_api.get_account_by_riot_id()` first. Retrieval uses the
[Riot Match-V5 API](https://developer.riotgames.com/apis#match-v5).

The service pages match IDs in batches of up to 50, fetches each match to identify
the player's champion, and only fetches timelines for matching games. It stops at
the requested successful analysis count, exhausted history, scan limit, or a blocking
request failure. `retrieval` reports requested/analyzed counts, scanned/matching
matches, failures and stop reason. Rate limits/auth failures stop requests rather
than triggering an uncontrolled retry loop. Failed matches can make the selected
sample incomplete; this is explicit even if replacement games reach the count.
No cache or database infrastructure was added. Versioned single-game results can
be serialized to JSON and cached later by match ID, PUUID and analysis version.

#### Aggregation semantics

- `aggregate_metrics` contains means, valid sample counts, missing counts and
  standard deviations. Duration-weighted CS/min is separately reported from the
  arithmetic mean of per-game rates. Duration ranges are included.
- Mixed roles or queues do not receive one pooled top-level gameplay average.
  `role_cohorts` separates role/queue, while `cohorts` further separates champion.
  General recurring patterns can span champions within a role/queue and report
  their champion distribution; champion-specific evidence remains separately visible.
- Patterns report occurrences, distinct supporting games, eligible games and rates,
  phase, underlying confidence and at most five example match IDs. Three supporting
  games and a 30% game rate are configurable screening criteria, not proof of a
  gameplay weakness. Confidence also respects per-game source confidence and a
  sample-size cap; one event repeated many times in one game is not cross-game recurrence.
- Jungler involvement is a recurring observation, never automatic tracking blame.
  Weakness trends use existing uncertain single-game candidates. Positive evidence
  includes participating in a favorable kill exchange followed by an allied capture;
  this does not prove the player's decision caused the capture or was optimal.
- Older/recent comparisons require at least three valid measurements in each half
  of a dated cohort. Direction means higher/lower, not a causal claim of improvement.
  Win/loss remains context and does not assign strengths or weaknesses.
- Missing dates exclude games from chronological comparison only. Missing metrics
  are not zero-filled. Unsupported engage/CC and resource-availability counts are
  `None`; empty timelines have unavailable event measurements. Fight participation
  refers to observed kill clusters, not every fight in the game.
- Duplicate match IDs are ignored with a count. Mixed PUUIDs/analysis versions and
  old results lacking aggregation fields raise a clear error; regenerate old analyses.

Multi-game reports contain summaries, cohort statistics and bounded references,
not embedded full game analyses. Detailed moments remain in single-game results.

### Evidence contract for the future Gemini consumer

`ANALYSIS_VERSION` is now `"4"` because multi-game evidence includes concrete examples
and factual death-ability summaries. Regenerate cached version-3 single-game analyses
before aggregation; `analyze_player()` rejects prior or mixed versions. Both report
types expose `schema_version: 2`: the existing structural schema is retained and the
analysis version distinguishes this additive evidence contract. An empty multi-game
report also identifies the current analysis version.

**Recurring patterns:** each pattern adds `examples`, containing at most
`MAX_PATTERN_EXAMPLES = 3` entries. Each entry includes `match_id`, occurrence
`timestamp`, `game_phase`, `champion`, `role`, `valence`, original occurrence `evidence`,
and `confidence` only when the source had it. Selection takes one occurrence per
distinct match, ordered by match ID and timestamp. One match cannot monopolize the
examples. These are supporting examples, not a representative statistical subsample.
`example_match_ids` remains available for compatibility. No game analyses or raw
timelines are embedded in the examples.

**Death abilities:** `death_ability_patterns` is added to each champion/role/queue
cohort and role/queue cohort. It is also directly available at the top level when
the report has one role/queue. Mixed-role/queue reports leave the top-level list
empty and direct consumers to the separate cohorts, rather than pooling rates.

Each entry has:

- `champion`: the attributed enemy champion, not the coached player's champion.
- `spell_name`: Riot internal name, trimmed and case-normalized; no semantic translation.
- `spell_slots`: observed slots, not inferred Q/W/E/R meanings.
- `death_occurrences`: distinct `(match_id, death timestamp)` records involving this ability.
- `games_with_occurrence`, `eligible_games`, and `game_rate`.
- `example_deaths`: at most three distinct-match examples with match ID, timestamp,
  phase, recorded damage, `player_champion`, and role.
- `interpretation`: recorded damage involvement only, without initiation or causality.

Only `ability_hits` with a resolved participant, resolved enemy relation, champion,
spell name and no conflicting/unresolved attribution are included. Unknown/allied
sources are excluded. Records of the same champion/spell within one death contribute
one death occurrence regardless of slot or repeated hits. Example damage sums those
reported records; it is not a count of casts or unique hits. Multiple deaths in one
game count separately, while that game contributes once to `games_with_occurrence`.

`death_ability_coverage` exposes `eligible_games`, `games_analyzed`, `observed_deaths`,
`deaths_with_reliable_enemy_ability_evidence`, `patterns_omitted`, and `semantics`.
Eligible games have timeline observation available and a structured deaths list;
this does not certify complete ability recording. The output retains at most
`MAX_DEATH_ABILITY_PATTERNS = 20` abilities per summary, sorted by distinct supporting
games, then deaths and name. Truncation affects only displayed entries, never counts
for retained abilities. An empty report has explicit zero coverage.

When exactly one champion/role/queue cohort exists, `death_context_counts`, `patterns`,
and `metric_direction` are additionally accessible at the top level. Aggregate
metrics, strengths/weaknesses, confidence groups, cohorts and champion filters keep
their existing fields. Top-level and cohort summaries are overlapping views: never
sum their counts together. Service retrieval metadata and public signatures are unchanged.

**How Gemini should consume the reports:**

- Specific game: use the default `analyze_game()` result. Death time, killer and
  contributors remain in the existing death object; health/gold are in
  `state_before_death`, sample ages in `evidence_quality`, phase in
  `game_state_before.phase`, and following events/window bounds in `team_outcome_after`.
  `personal_outcome` remains separate. No duplicate death-schema fields were added.
- Recent games: use `analyze_player()`/`analyze_recent_games()` metrics and cohorts,
  recurring-pattern examples and death-ability summaries. Cite example match IDs and
  timestamps rather than reconstructing raw timelines.
- Champion: use `analyze_champion()` and its champion filter, sample size, top-level
  evidence (when homogeneous), and retrieval metadata. Multiple roles/queues must
  still be interpreted separately. `complete: false` must remain visible to the user.

Spell involvement does **not** establish initiation, CC, engage importance, positioning
error or mistake causality. Empty ability lists do **not** establish that no engage
occurred. `engage_cc_deaths` remains `None`, and `important_spell_hits` remains empty
without audited threat metadata. Missing snapshots, wards, wave evidence or candidates
likewise cannot establish safety, visibility, available farm or an error-free decision.
All earlier limitations remain in force. Python emits no final coaching text and
makes no Gemini calls. Caching, query parsing and application integration remain outside
this package change. Never send diagnostic `include_windows=True` output by default.

```python
parsed_match = parse_match(raw_match, puuid)
player_id = parsed_match['player']['participant_id']
opponent = parsed_match['opponent']
timeline = parse_timeline(raw_timeline, player_id,
                          opponent['participant_id'] if opponent else None)
analysis = analyze_game(timeline, parsed_match)
```

`analyze_game(timeline, match)` retains `cs_analysis`, `major_swings`, `farm_windows`,
`deaths`, `fights`, and `coaching_signals`. It adds `schema_version`, `game_context`,
`resource_events`, `resource_opportunities`, `resource_opportunity_status`, and
`limitations`. Ordinary windows are omitted by default. Use
`analyze_game(timeline, match, include_windows=True)` for the full diagnostic windows;
do not send that diagnostic output to Gemini. Major swings omit full participant
snapshots, while `create_windows()` still provides them.

An absent counterpart produces `None` matchup metrics; personal and team measurements
continue. Parsed participant maps use integer IDs in memory, as before.

Deaths retain existing flat fields. All named non-basic damage now belongs in
`ability_hits`. The retained compatibility field `important_spell_hits` is empty:
no audited threat metadata is configured. Raw normalized `damage_sources` also keep
basic attacks, unnamed damage and non-champion sources. Nautilus hook evidence is
preserved without adding a champion-specific rule or inferring which ability initiated
the fight. Reported damage is not proof of the complete combat sequence.

`cause_candidates` now contains only cautious combined-evidence inferences. Jungler
involvement is a fact, not a cause candidate. Repeated jungler involvement is a count
with timestamps, not a claim of poor tracking. Repeated signals cannot turn generic
ability damage into engage errors or normal two-enemy bot fights into isolation.

`personal_outcome` keeps decision quality undetermined. `team_outcome_after` contains
following events and sampled team gold changes, with actual sample timestamps and
an explicit non-causality label. Positive team gold never marks a death good.

## Measurements and inference decisions

- Overall CS/min uses Match-V5 final CS and duration in seconds. Lane minions per
  estimated wave and post-lane CS/min use an explicitly recorded sample boundary.
  The inherited 98-second first-arrival / 30-second cadence is a configurable rough
  benchmark, not patch-certified wave availability. Lane-minion counts do not prove
  which lane the player farmed or distinguish access from last hitting.
- The earlier of a lane outer-turret loss and the 14-minute benchmark suggests a
  transition. Phase labels also consider observed structure losses. These are weak
  labels, not exact lane-phase reconstruction; non-Summoner's Rift phase is unknown.
- Low farm is normalized by window duration. Deaths before a window remain relevant.
  Alive samples showing resumed CS collection can end the fallback downtime inference;
  a dead sample can extend it. The 90-second fallback is not an exact respawn timer.
- Kill/assist activity, recorded objective participation, shopping, sampled death,
  game ending, repeated sampled grouping and teammate lane-CS gains provide alternative
  explanations. Support low CS is not diagnostic. Nearby teammate absorption requires
  agreement at both window endpoints and remains an inference.
- Health/economic context uses a strictly earlier snapshot, never the death-frame
  zero-health observation or a later snapshot. Sample ages are exposed. Low-health
  inference requires a sample at most 30 seconds old plus combat involvement.
- Possible isolation requires at least three event contributors, multiple sampled
  enemies and two complete pre-death ally samples without nearby allies. Even this
  is only medium/low confidence. Sampled absence never removes combat participants.
- Kill clusters remain active for 30 seconds within 3,500 map units, including when
  unrelated kills interleave. Missing positions require shared participants. First
  and last kills are observed bounds, not claimed full fight duration.
- Conversion windows retain both teams' captures. Only allied captures count as
  allied conversion. Truncated end-game windows cannot generate missing-conversion
  candidates. Overlapping windows can share events and do not establish causality.
- Structure `team_id` remains the destroyed structure's owner; `gaining_team_id`
  identifies the other team, including when the killer is a minion. Objective names
  are passed through without a fixed list of season-specific monsters. This follows
  the structure fields shown in [Riot's timeline example](https://gist.github.com/RiotTuxedo/ab04ac027546f711ce820faed394295b).

Confidence values are coarse heuristic labels, not calibrated probabilities. Named
constants at the top of the analyzer make thresholds easy to review and change.

## Deliberately undetermined

`resource_events` reports actual plates, structures and neutral captures, participation
records, sampled alive states and nearby recent kill timestamps. `resource_opportunities`
is empty because the current evidence does not establish available waves, plates,
camps or free objectives. Unexplained low farm is a review candidate, not proof of a
missed wave or bad last hitting.

No exact safe/unsafe side-wave verdict, facecheck, engage-range violation, turret-safety
claim, fog-of-war reconstruction, exact inventory valuation, recall timer or respawn
timer is asserted. Ward events often lack positions; absence of nearby ward evidence
does not mean no vision. Structure loss history does not reconstruct all surviving
turret positions or inhibitor respawns. Spent gold is an approximation that includes
consumables, sales and other transaction effects. Power differences remain metrics,
not automatic causes of death. Final coaching and spell semantics belong downstream.

## Validation

### Follow-up accuracy changes

- A snapshot showing the player dead, or preceding another player death, is not
  reused as current-encounter context. It is retained in `historical_snapshot`;
  `state_before_death` and encounter health/power comparisons become unavailable.
  `encounter_context_status` explains why. Isolation cannot combine samples across
  player lives. Historical team-gold measurements remain available with their bounds.
- Damage source names are compared with known match champion names (ignoring case
  and punctuation). A name identifying a different champion produces `identity_conflict`.
  The original ID/name and mapped `participant_champion` are retained, but resolved
  participant/team attribution is unknown. Existing `source_team_id` and
  `source_team_relation` describe only the participant-ID mapping; consumers should
  use `resolved_participant_id` and `resolved_team_relation` for attribution.
  Unrecognized names are not reassigned to a champion. Common ownership limitations
  appear once in `limitations`, with per-source notes only for exceptional cases.
- Timeline parsing preserves damage records for all champion kills. Fight
  `participants` now includes unambiguous enemy damage contributors as well as
  killers/victims/credited assists; `participant_evidence` records these distinctions.
  Conflicting or allied damage attribution alone cannot add a combat contributor.

- Milestone metrics choose the nearest snapshot within `MILESTONE_SAMPLE_TOLERANCE`
  (5 seconds) and expose the signed offset. Missing benchmark snapshots produce
  unavailable metrics rather than silently using the previous minute. Tower-loss
  boundaries can still use the preceding frame with its offset recorded. Strictly
  pre-death sampling is unchanged.
- Death outcomes add `event_window` and `gold_window`. These expose event bounds,
  gold sample bounds, included pre-death time, post-death coverage and the uncovered
  event tail. Existing flat outcome fields remain compatible; gold is not interpolated
  to the event boundaries.
- Both `damage_sources` and `ability_hits` preserve reported damage and add source
  team relation (enemy/allied/unknown). Attribution does not verify the owner of an
  item or environmental effect. Allied attribution does not establish an allied attack.
- `cause_candidate_status` explains that empty candidates do not establish an
  error-free death. `print_death_summary()` prints sample timestamp/age, health,
  level and gold context, attribution, and separate event/gold windows.
- Fight conversion rules were not changed in this follow-up.

The tests cover 29:58 post-death downtime, normal bot 2v2, Kai'Sa spell false positives,
preserved hook damage, jungler involvement, positive global outcomes, combat/position
disagreement, absolute farm metrics, structure attribution, interleaved fights,
empty/short games, missing opponents/health, compact output, enemy conversion,
truncated conversion windows, resumed farming, teammate absorption and unknown
objective names. Fixtures are synthetic: they validate logic, not the replay-reviewed
Yunara match, which was not supplied as raw data. No live Riot requests were made.

The cross-game tests cover structured-only/JSON-roundtrip aggregation, means and
missing-data denominators, recurrence across distinct games, champion filtering,
roles/queues, strengths in losses, chronology, sample sizes, duplicate/version/player
validation, and compact output. Mocked service tests request 20 champion games across
58 overall matches, verify pagination and timeline filtering, and exercise scan-limit,
empty-history and rate-limit partial results. These tests make no live API calls.

Version-4 tests add bounded/distinct recurring examples, source-confidence preservation,
ability death/game deduplication, case/slot normalization, excluded attribution conflicts,
unavailable engage semantics, cohort/filter boundaries, ability output caps, JSON round
trips, payload-size checks and prior-version rejection. All tests remain offline.
