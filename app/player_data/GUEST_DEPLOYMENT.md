# Guest trial rollout

## Apply manually

1. Back up staging and inspect its actual schema. The repository does not contain the baseline Supabase DDL. Confirm that chat sessions accept caller-generated UUID IDs, have user_id/title/created_at, and chat messages accept session_id/role/content/used_context/created_at and generate their other required fields. Confirm ownership RLS and account deletion cascades. Do not loosen RLS. Check signing in and deleting an expendable staging account.
2. Apply migrations **202611150001_guest_trial.sql**, then **202611150002_guest_claim.sql**. Neither was applied to a hosted database by this implementation. The new schema is private; do not add wg_trial to Supabase exposed schemas. Do not grant anonymous/authenticated users either RPC.
3. Configure server variables in the root .env.example. Generate two independent secrets. Share INTERNAL_PROXY_SECRET only between the trusted Next.js server and FastAPI. GUEST_IP_HMAC_SECRET is backend-only. Configure HTTPS WAVEGUIDE_BACKEND_URL on Vercel; retain the existing NEXT_PUBLIC_API_URL, Supabase public config and backend-only provider/service credentials. Do not put secrets in NEXT_PUBLIC variables, logs, error monitoring payloads, or client storage.
4. FastAPI must support starting a Python child process, outbound calls, and the configured request duration. Verify CPU, memory, worker concurrency, child process support and request timeout on the actual host. Default hard work deadline is 240s; proxy timeout is 285s and route maxDuration 300s. Configure the hosting plan accordingly or lower the backend deadline. The child has its own deadline and a lease watchdog. A failed network delivery can be replayed; it is not a reason to increment twice. Never deploy a fallback in-memory quota.
5. Enable WG_GUEST_ENABLED=true on staging after migrations, test guest creation through the frontend, then enable in production. Keep HTTPS on both hops. Local Next.js development uses loopback IP only. Production requires direct Vercel ingress and its x-vercel-forwarded-for header; it fails closed when missing. Do not set VERCEL=1 on an untrusted custom reverse proxy. Existing authenticated clients can continue using a verified bearer directly; with the feature enabled, these chat calls also pass through global DB admission. A failed bearer never falls through to guest mode. Other account endpoints keep their original auth.
6. In Supabase Cron (pg_cron), schedule hourly cleanup with a trusted database owner: select public.waveguide_trial('cleanup', '{}'::jsonb);. For example, run the following once after enabling Cron. Verify runs in the dashboard and alert on failures. The schedule is **not installed automatically**.

    select cron.schedule('waveguide-guest-cleanup', '17 * * * *',
      $$select public.waveguide_trial('cleanup', '{}'::jsonb)$$);

7. Vercel Dashboard → Firewall → custom rules: match method AND path, then choose the rate-limit action where your plan supports it. Start in log mode and tune with legitimate traffic. Suggested per-source-IP thresholds: POST /api/trial/guest/session 10/min (creates capped separately in DB), POST /api/trial/chat 30/min, POST /api/trial/guest/claim 10/min, GET /api/trial/guest/status and /api/trial/guest/sessions* 60/min. Prefer a 429 response. Verify rule order, actual paths, rollout environment and analytics before enabling enforcement. Do not add CAPTCHA or Cloudflare. Firewall rules have not been created by this code. Vercel protects only requests passing through it; FastAPI independently authenticates the proxy and enforces database budgets.
8. Confirm email verification takes the visitor back to the same WaveGuide origin via the existing Supabase confirmation route. The guest cookie is host-only, HttpOnly, Secure, SameSite=Lax, path / and valid for 90 days. The guest history stays unclaimed during verification. Opening the email on a different device does not move its cookie: sign into the account on the original browser to claim. Clearing browser cookies before claiming loses access.

## Behavior and controls

- Five **successful** coaching responses per guest token, 1 in flight. The browser holds 32 random bytes encoded as an opaque cookie; PostgreSQL holds only its SHA-256 digest. No guest auth.users, client-provided usage, fingerprint or IP-based identity.
- PostgreSQL admission locks only short metadata operations. Rate attempts are counted before model or Riot work. A unique active request per guest and a fenced lease reserve the fifth slot. Successful charge, conversation/messages, replay payload, and lease settlement commit together. Empty/error replies do not consume quota. Nonchargeable clarifications can be saved to keep conversational context. Direct Riot failures, Gemini failures and provider timeouts release the reservation. A completed 20-game analysis costs one guest success.
- Each guest submission has a UUID. Retries of the same ID and payload replay the finalized answer; changed inputs conflict. Session storage remembers only the pending digest and ID, never the token or quota. The lifetime counter never resets daily. PostgreSQL rejects further submissions before Gemini and Riot. The composer remains blocked even when the signup modal is dismissed.
- Fixed UTC windows: three new guest sessions/IP/day, fifteen guest successes/IP/day, thirty attempts/IP/hour, ten attempts/session/ten minutes. In-flight successes temporarily occupy a daily IP slot. Limits and Retry-After are separate from signup enforcement. Shared networks can hit limits; cookie clearing, incognito, VPNs and distributed clients cannot be perfectly identified.
- Global AI budget reserves up to two model calls (parser plus generator) per admitted chat, even if a deterministic error later uses fewer. Defaults: 120 calls/min, 4,000/day, 12 concurrent chats, 16 KiB body, 1,500 guest message chars, server-owned history, 2,048 parser and 4,096 response output tokens. Budgets do not change the existing 20/day account quota or 20-game analysis cap.
- Requests renew a 120s lease every 20s. Worker stops on deadline or loss of heartbeat; late workers cannot finalize a replaced lease. No DB transaction is held during provider execution. External services do not offer transactional exactly-once execution after a crash before persistence: recovery may repeat unfinished work but cannot double-charge or replay completed calls as new work.
- Unclaimed transcripts and replay records expire with the 90-day session on cleanup. Expired windows have a short cleanup grace period. Claims copy chats and structured context transactionally into account-owned tables, then remove the guest copies. A minimal claim marker permits same-account retries only. Deleting the account cascades the marker; verified account ownership still governs transferred chats.
- Disable WG_GUEST_ENABLED on all backend instances for an emergency stop. Keep the database and signing secrets intact during rollback; do not drop unclaimed histories. Redeploy the previous frontend if the trial should no longer be presented.

## Validation / handoff

Backend tests: run the project virtual environment's Python with -m unittest discover in app/player_data. Database tests under supabase/tests use disposable schemas and never take production credentials. Install @electric-sql/pglite in a temporary development directory, set PGLITE_MODULE to its module path, and run guest-db.cjs and guest-claim.cjs with Node. For the multi-connection test, install embedded-postgres and pg outside the project, set WG_TEST_NODE_MODULES to that node_modules directory and run guest-concurrent.cjs against an unused loopback port. Do not add these test binaries to the deployed app.

For the UI run npm run lint, npm run build and the existing account tests. Run frontend/tests/guest-trial.cjs, responsive.cjs and build-cards.cjs against a local production preview (FRONTEND_TEST_URL, WAVEGUIDE_PLAYWRIGHT). Browser tests intercept external services. Production smoke: test five responses including match analysis, an error/retry, refresh and same-cookie browser restart, account claim after email verification, account deletion, unauthorized direct origin requests, expired leases, and cleanup job logs. Monitor rate-limit/error counts without logging tokens, IP headers, authorization headers or chat payloads.

References: [Vercel request headers](https://vercel.com/docs/headers/request-headers), [Vercel WAF rate limiting](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting).
The assembled model prompt is also capped (WG_MAX_PROMPT_CHARS, default 750000). Oversized evidence returns a nonchargeable error instead of silently truncating a requested analysis. Gemini calls have a 60-second HTTP timeout and one attempt so SDK retries cannot multiply the global request budget.
